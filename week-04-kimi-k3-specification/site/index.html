Why formalize a model report?

A technical report can put an equation in one line while leaving shapes, indexing, state updates, and implementation choices to the reader. That is pretty standard — no report has room to spell everything out. But Lean has a different standard: it makes those choices explicit enough for a type checker and proof kernel to verify them.

In Lean, every object has a type and every proof reduces to a term checked by a small trusted program called the kernel. A theorem can still be confusing or poorly explained, but it cannot quietly call an undefined operation. The definitions have to actually line up. That's the whole point.

Over the last few years, mathematicians have shown that this style can reach well beyond textbook exercises. The Liquid Tensor Experiment formalized the main theorem of a contemporary condensed-mathematics argument. Its online blueprint placed the human proof beside links to Lean declarations and a dependency graph, so you could follow the logic at both levels at once. The Polynomial Freiman–Ruzsa project used the same approach for a new additive-combinatorics proof; a distributed collaboration reached a proof with no unfinished placeholders in December 2023. In both cases, the act of formalizing exposed missing hypotheses, forced cleaner definitions, and turned the paper into something a machine could actually check — not just read.

I wanted to try this with a neural-network paper. The tricky part is that most AI papers aren't really theorem papers. They describe systems. You get architecture diagrams, training recipes, benchmark tables, and evaluation conditions, all bundled together, each requiring a different kind of evidence. It's easy to lose track of what's been verified versus what's just described. Kimi K3 covers architecture equations, a multi-stage training recipe, distributed-systems design, and benchmark results all in one document. That mix made it interesting to work with.

What I found is that formalizing a neural-network report changes how you read it. Instead of just following the math, you start asking: which function does this equation actually denote? What state has to be made explicit? Which shapes should the type checker reject? What theorem would capture the intended behavior? And — the question that's hardest to answer — what evidence would connect that theorem to the code used for the released model?

This site lays out what's been checked for each part of the K3 report. The architecture equations and selected training equations have Lean definitions. For the main language components and the three MoonViT stages, each operation is written twice: once as a readable tensor function and once as a typed TorchLean graph. Theorems prove the two versions return the same tensors. The final one-token theorem connects the typed graph to a packed reference calculation. But connecting that to the public list-based model is still open. Training data, CUDA kernels, benchmark runs, and the 2.78-trillion-parameter checkpoint all require evidence that's outside what Lean can provide.

The eventual goal is to load the public weights, run them through the verified graph, and prove which equalities survive when you move to low-precision fused kernels. Right now the development checks one route-staged, packed text-token step for any well-formed choice of dimensions. The checkpoint itself doesn't run yet — that's the next big step.

Lean keeps the program and the proof together

This project would make less sense in a proof language that could only describe mathematics. Lean is both an interactive theorem prover and a functional programming language. "Functional" means the program is built by composing functions. "Pure" means a function's result depends on its stated inputs, not on hidden state elsewhere. "Dependent types" let a value like a tensor dimension appear inside a type, so shape errors become type errors. A tensor operation can therefore run, its dimensions get checked before it runs, and a theorem about its result can live in the same file.

Purity matters here for a concrete reason. When you write a reference equation for a neural-network layer, you want it to say what the layer computes, not how it's implemented. K3's smooth SiTU cap is just a function of two numbers — it doesn't need to know what GPU it's on, whether the kernel is fused, or whether weights are stored in four-bit format. Writing it as a pure function makes that separation explicit and checkable. The theorem below proves a uniform bound for the paper's two cap values for every pair of real preactivations, with no caveats about hardware or floating-point behavior.

def softCap {α : Type} [Context α] (cap x : α) : α :=
  cap * MathFunctions.tanh (x / cap)

theorem paper_caps_bound (gate up : ℝ) :
    |scalar 4 25 gate up| ≤ 100 := by
  have h := abs_scalar_le_mul_caps (gateCap := (4 : ℝ))
    (upCap := (25 : ℝ)) (by positivity) (by positivity) gate up
  norm_num at h ⊢
  exact h

Dependent types catch a different class of bug. A KDA state carries its two dimensions in the type Tensor α [keyDim, valueDim]. A matrix with those axes reversed is a different type entirely — the type checker treats them as incompatible. When the graph connects an output wire to the next layer's input, Lean checks that the shapes agree before any tensor is ever created. Dimension mistakes that would silently produce wrong results in PyTorch show up as type errors during Lean elaboration.

Proof and execution still have different jobs, and it's worth being concrete about this. The real-valued reference function is written for algebra — it uses real numbers, exact arithmetic, and readable notation. The GraphSpec part of TorchLean records the same computation as typed graph nodes, a kind of wiring diagram where every wire has a shape. TorchLean can then lower that graph into code that actually runs. A denotation theorem bridges the two: it proves that evaluating the graph produces the same result as calling the readable reference function. If you later want to reason about a fused low-precision GPU kernel, that requires yet another step — a separate refinement proof showing the kernel approximates the graph within some stated error. The structure is: clean math, then wired graph, then hardware kernel, with theorems connecting each pair.

Working this way changes how I read the K3 report. Instead of asking "does this make sense," I find myself asking a different set of questions: which function does this equation actually denote? What state has to be made explicit? Which shapes should the type checker reject? What theorem would capture the intended behavior — and is it actually provable? What evidence would connect that theorem to the code running the released model? These questions don't always have clean answers, but asking them precisely is part of what makes this kind of work different from reading a paper and nodding along.

Enough Lean to follow the proofs

Lean notation looks intimidating at first, but most of the blocks below are asking the same three questions: what goes in, what comes out, and what's been proved about what happens in between? Once you see that pattern, the dense syntax becomes a lot more readable.

Start at the colon

The colon in a Lean definition separates a name and its arguments from its type. In the block below, step takes a state and an input and returns a pair: the updated state and an output tensor. The return type appears after the final colon. Notice that the state type is the same before and after the call — that's not a coincidence. It means the update cannot quietly change the matrix dimensions. The symbol := means "is defined to be," and everything after it is the actual calculation.

def step
    (state : State α keyDim valueDim)
    (input : KDAStepInput α keyDim valueDim) :
    State α keyDim valueDim × Tensor α (.dim valueDim .scalar) :=
  let state' := update state input
  (state', read state' input.query)

Type variables and Greek letters

The Greek letter α (alpha) names the scalar type. For proofs, it's usually the real numbers. For a compiled graph, it might be a 16-bit float or some other number system. The same definition works for both — you just supply a different α. This is what mathematicians call abstraction over the coefficient field, though it sounds less scary when you think of it as "this formula doesn't care what kind of number you plug in, as long as the operations make sense."

A type like Tensor α [4, 2] means a tensor of α-values with four rows and two columns. The shape [4, 2] is right there in the type, not hidden in a runtime assertion. Lean checks it while reading the program — before anything is run, before any tensor is allocated. If two tensors have incompatible shapes and you try to connect them, that's a type error, not a silent bug you discover later.

Fin, List, and Tensor — three different ways to hold data

Fin n is an integer that Lean knows is between zero and n − 1. It's not just a regular integer with a runtime bounds check — the constraint is baked into the type itself. So if an expert ID has type Fin 896, an out-of-range expert ID is literally not a value of that type. You can't accidentally pass 1000 where at most 895 is valid.

A List can change length over time — you push items onto it, or you process it token by token. A tensor shape, on the other hand, is fixed. That distinction shows up repeatedly in this development: the reference model often uses lists because it's describing a causal sequence that grows one token at a time. The typed graph uses fixed tensor axes because a graph needs static shapes to be wired up. Bridging those two representations — proving that a list-based reference and a tensor-based graph compute the same thing — is one of the main technical challenges.

What structure, def, and theorem do

A structure is just a record: a named bundle of fields. It might hold a model's weight matrices, or a cache, or a probability value along with a proof that the value is positive. A structure is data, not a computation. Don't read too much into it on its own.

A def defines a function or value. It consumes structures and produces new ones, or produces tensors. This is where the actual computation happens. A theorem makes a claim about what a def returns. After theorem, everything up to := by is the statement being proved. The lines after by are tactic commands that Lean uses to build a proof term that its kernel verifies. If you see simp or ring or linarith, those are automated proof tactics — they search for a proof the way a computer can, handling routine algebraic steps so you don't have to.

TorchLean's Term type

TorchLean adds one more layer on top of regular Lean. A Term Γ shape is a node in a computation graph — think of it as a typed wire carrying a tensor of shape shape, with the external inputs it depends on listed in Γ. You build expressions by composing Term values with Term.op, naming each primitive operation explicitly. Term.eval gives the graph a mathematical meaning by plugging in actual tensors. specFwd evaluates a whole graph model at once.

The most important pattern to recognize is the denotation equality: model.specFwd params inputs = referenceFunction inputs. That equation says the graph and the reference function produce the same result. It's the key theorem in each section — the one that ties the wiring back to the readable math you can inspect without knowing how TorchLean works.

A practical tip when reading later blocks: start with the type signature and the final theorem, and only then look at the middle. The signature tells you what types flow in and out. The theorem tells you what claim is being made. The middle is the wiring those two claims force you to inspect.

Start with an ordinary transformer

A language model is, at its core, doing one simple thing over and over: given everything it's seen so far, assign a probability to what comes next. The scale of K3 — 93 layers, 2.78 trillion parameters, a million-token context — can make that loop hard to see. It helps to strip it back to the basics first.

  1. 1

    Tokenize. The text gets split into vocabulary pieces called tokens — roughly word fragments — and each gets an integer ID. "unhappy" might become two tokens: "un" and "happy." Everything downstream works with these integer IDs.

  2. 2

    Embed. Each token ID selects a learned vector from a lookup table. A vector is just an ordered list of numbers — in K3's case, 7,168 of them per token. Those numbers don't have predetermined meanings; the model figures out during training which coordinates to use for which concepts.

  3. 3

    Ask and match. Three learned matrices project each token's vector into a query, a key, and a value. The query asks "what am I looking for?" The key says "here's what I offer." The match score between a query and a key tells you how relevant that past token is to the current one.

  4. 4

    Mask the future. When predicting the next token, a position can only look at itself and earlier tokens, never later ones. This causal mask sets future match scores to negative infinity, so they become zero after softmax. At inference time, there are no future tokens — so the mask is mostly a training convenience.

  5. 5

    Weight the answers. Softmax converts all the match scores for one token into nonnegative weights that sum to exactly one. Think of them as percentages: "I'm paying 40% attention to the word three positions back, 30% to the start, 20% to myself, and 10% spread across the rest." These weights then form a weighted sum of the value vectors.

  6. 6

    Update and continue. A residual connection adds the old vector back to the attention output. Then a feed-forward network processes that updated vector, and another residual addition carries the result to the next layer. The residual is the reason deep transformers can work: a block that learns nothing useful just leaves the vector unchanged instead of destroying it.

The standard attention equation compresses steps three through five into one line. Capital letters stand for tables with one row per token: holds the queries, the keys, and the values.

  1. takes every allowed query–key dot product. A dot product multiplies matching coordinates and sums them, giving one match score per position pair.
  2. rescales those scores. Without it, scores would grow larger just because the key vectors have more coordinates, which would push softmax toward picking just one token instead of a smooth mixture.
  3. is the causal mask — large negative values for future positions that softmax then drives to zero.
  4. The final multiplication by forms a weighted combination of the value vectors from all allowed positions.

Real decoders run this calculation across many attention heads in parallel. Each head uses its own separate query, key, and value projection matrices, so different heads can learn to pay attention to different things — one might track syntactic structure, another semantic role, another pronoun reference. K3 uses 96 heads. Their outputs get concatenated and projected back to the model width. This also explains why cache sizes later multiply by 96.

Attention as written doesn't know token order — a permuted sequence looks the same to the dot products. Models fix this with positional encodings. K3 uses rotary positional embeddings (RoPE) in its MLA layers: a rotation applied to queries and keys that encodes position by making dot products decay smoothly with distance. KDA, which most K3 layers use instead, doesn't need RoPE at all — its recurrent state naturally depends on the order tokens arrive.

The residual stream is often underappreciated. Every block computes , and the representation going into the next block is . If is small, the original vector survives nearly unchanged. This means a block that hasn't learned anything useful yet just passes the signal through. It also means later blocks can read information that was written earlier, because the residual stream accumulates every block's contributions as a sum rather than overwriting. K3 extends this further with AttnRes, which can retrieve from earlier layer sums directly.

The feed-forward half of each block is what holds most of the model's parameters. It takes the attention output, projects it up to a wider hidden space, applies a nonlinearity, and projects back. In K3 this becomes a mixture-of-experts layer rather than one dense network — each token only activates a small fraction of the available capacity. But the basic pattern is the same.

Training processes many token positions in parallel. Inference is different: the model generates one token, appends it, and runs again. Keys and values from previous steps don't change, so implementations save them in a KV cache. The cache grows by one entry per token per attention layer. This is the trade-off the original transformer design made: instead of compressing history into a fixed recurrent state (like an LSTM would), it keeps the full history directly accessible. That's powerful but expensive for long contexts. Most of K3's architectural complexity exists to manage exactly this trade-off.

The Attention Is All You Need paper from 2017 made this pattern work at scale. Since then, every major decoder model has changed normalization, positional encodings, activations, and attention layout. But the alternating rhythm — attention to mix between positions, then feed-forward to transform within one position, then residual addition, then the next layer — stayed recognizable all the way through to K3.

Why K3 needs more than an ordinary transformer

The transformer scales cleanly on paper: add layers, widen the vectors, and train on longer sequences. Machines feel each of those choices differently.

Full attention and its KV cache grow with sequence length

For a full causal sequence of length , one attention layer has permitted query–key pairs. Efficient kernels can avoid storing the full score matrix, but they do not turn quadratic attention into a constant-size recurrence. During generation, the KV cache grows by one entry per new token in every full-attention layer.

Models reduce this cost in two broad ways: store less information for each previous token, or replace the growing table with a fixed state that is updated after every token. K3 uses both. Multi-head Latent Attention (MLA) keeps one compressed entry for each earlier token, so a layer can still look back at individual positions. Kimi Delta Attention (KDA) keeps a fixed-size recurrent matrix instead, so its memory does not grow with sequence length.

Width makes dense computation expensive

The feed-forward network often owns most of a transformer's parameters. Sparse mixture-of-experts models keep many feed-forward networks but route each token through only a few. The Switch Transformer showed how this could reach trillion-parameter scale years before dense models could afford the same count. The bargain comes with routing, load balancing, and communication problems. Unused experts are cheap arithmetically and still expensive to store and move.

Depth compresses history into one residual stream

A conventional residual stack carries a single running sum. By layer ninety, that vector contains contributions from every earlier block, but the current layer cannot directly choose an old representation. It receives the sum. Attention Residuals changes the depth path: block summaries remain visible and the current layer retrieves a weighted mixture. K3 groups layers so this extra history does not grow one entry at a time forever.

Images have to become language-model inputs

A vision transformer turns an image or video into patch tokens. A multimodal language model must decide where those tokens enter, how their feature width matches the language backbone, and whether training treats visual and text examples as one sequence from the beginning. Those are architectural contracts, not preprocessing trivia.

Kimi's earlier Kimi Linear work developed Kimi Delta Attention as a gated delta-rule recurrence and paired mostly recurrent layers with occasional full attention. K3 brings that hybrid into a much larger system, adds depth retrieval and a latent expert space, and trains the result as a native multimodal model.

How K3 handles sequence length, depth, width, and vision

KDA and MLA split the sequence problem: KDA carries a fixed-size summary forward, while periodic MLA layers can still inspect individual cached tokens. AttnRes retrieves earlier summaries across depth. Stable LatentMoE expands capacity across width without running every expert. MoonViT-V2 turns images and video into vectors the language backbone can consume.

The resulting model has 2.78 trillion parameters, activates 104 billion of them for each token, accepts text, images, and video, and supports a context window of 1,048,576 tokens. Moonshot released the weights. This gives the formalization a concrete object to aim at, rather than an architecture reconstructed from an API description.

The type chooses the right cache and update

The type matters because step consumes it. Pattern matching on the mixer selects both the state representation and the transition; forward then scans that transition over the tokens. The theorem states a behavior of the scan, rather than restating a field of a record.

def step (mixer : SequenceMixer α cfg decayRank)
    (state : mixer.CausalState)
    (token : Tensor α (.dim cfg.hiddenDim .scalar)) :
    mixer.CausalState × Tensor α (.dim cfg.hiddenDim .scalar) :=
  match mixer with
  | .kda layer logFloor => layer.scanStep logFloor state token
  | .mla layer => layer.step state token

def forward (mixer : SequenceMixer α cfg decayRank)
    (tokens : List (Tensor α (.dim cfg.hiddenDim .scalar))) :
    List (Tensor α (.dim cfg.hiddenDim .scalar)) :=
  (CausalScan.run mixer.step mixer.initialState tokens).2

theorem forward_length (mixer : SequenceMixer α cfg decayRank)
    (tokens : List (Tensor α (.dim cfg.hiddenDim .scalar))) :
    (mixer.forward tokens).length = tokens.length := by
  exact CausalScan.outputs_length mixer.step mixer.initialState tokens

KDA and MLA therefore share one causal interface without sharing an untyped cache. The schedule proof still belongs to the model value, but it is not the formalization by itself.

First ask what the theorem actually reaches

The K3 report moves between four kinds of claim. An equation describes a mathematical function. An architecture diagram says how functions and state fit together. A systems section says how a machine executes them. An evaluation section reports what happened in an experiment. Lean can help with all four, but it cannot turn them into the same kind of evidence.

mathReadable tensor function

What result should this operation return over the chosen scalar semantics?

graphTyped TorchLean graph

Do the operations compose with the intended shapes and explicit state?

running codeRuntime implementation

Does a finite-precision, fused implementation agree with that graph?

experimentMeasured result

Did the released checkpoint, training job, or benchmark produce the reported result?

Most theorems here prove that a graph returns the same tensor as the readable mathematical function. That checks the model's meaning and wiring. It does not yet verify a CUDA kernel, a training run, or a benchmark score.

This is the readable version. It says what the expert computes and leaves graph wiring, mutable references, and kernels out of the equation.

2. The same computation as typed nodes

def Expert.term {Γ : List Shape}
    (inputDim hiddenDim outputDim : Nat)
    (input : Term Γ [inputDim])
    (gateWeight upWeight : Term Γ [inputDim, hiddenDim])
    (downWeight : Term Γ [hiddenDim, outputDim])
    (gateCap upCap : Term Γ .scalar) : Term Γ [outputDim] :=
  let gate := Term.op (PrimOp.vecMat inputDim hiddenDim)
    (.cons input (.cons gateWeight .nil))
  let up := Term.op (PrimOp.vecMat inputDim hiddenDim)
    (.cons input (.cons upWeight .nil))
  let cappedGate := softCapTerm [hiddenDim] gateCap gate
  let sigmoidGate := Term.op (PrimOp.sigmoid [hiddenDim])
    (.cons gate .nil)
  let gated := Term.op (PrimOp.mul [hiddenDim])
    (.cons cappedGate (.cons sigmoidGate .nil))
  let cappedUp := softCapTerm [hiddenDim] upCap up
  let hidden := Term.op (PrimOp.mul [hiddenDim])
    (.cons gated (.cons cappedUp .nil))
  Term.op (PrimOp.vecMat hiddenDim outputDim)
    (.cons hidden (.cons downWeight .nil))

Every intermediate has a shape in its type. Because this is an ordinary term rather than an opaque “expert” node, graph composition and lowering can still inspect it.

3. The graph is tied back to the equation

theorem Expert.specFwd_eq_forward
    (expert : KimiK3.Expert ℝ inputDim hiddenDim outputDim)
    (input : Tensor ℝ [inputDim]) (gateCap upCap : ℝ) :
    (Expert.model inputDim hiddenDim outputDim).specFwd
        (Expert.parameters expert)
        (Expert.inputs input gateCap upCap) =
      expert.forward gateCap upCap input

The graph can then lower through TorchLean's toProgram API. That lowering is a real executable path, but this development does not yet prove program execution equal to specFwd or connect it to Moonshot's fused kernels.

The first definition is the mathematical reference. It computes ordinary tensors. Read its local names in order: normalize the stored sources, score them, exponentiate the scores, divide by their sum, and use the resulting weights to mix the original sources.

def attendPacked {sources : Nat} (hModel : 0 < modelDim)
    (query : Tensor α (.dim modelDim .scalar))
    (values : Tensor α (.dim sources (.dim modelDim .scalar))) :
    Tensor α (.dim modelDim .scalar) :=
  let unitScale := Tensor.ones [modelDim]
  let normalized := Tensor.dim fun row =>
    RMSNorm.scalePositive hModel (Spec.get values row) unitScale
  let scores :=
    vecMatMulSpec query (Tensor.swapAdjacentAxes normalized 0)
  let kernels := Tensor.expSpec scores
  let denominator := Tensor.sumSpec kernels
  let weights :=
    Tensor.mapSpec (fun weight => weight / denominator) kernels
  vecMatMulSpec weights values

K3 adds depth and experts without widening the residual stream

Kimi K2 already had more than a trillion parameters, but K3 does not obtain its extra capacity by widening the residual stream. Both models keep a hidden dimension of 7,168. K3 grows from 61 to 93 language-model layers, expands the routed pool from 384 to 896 experts, doubles the active routed experts from eight to sixteen, and adds a second shared expert. The expert hidden dimension rises from 2,048 to 3,072. The result is 2.78 trillion stored parameters and 104.2 billion active parameters per token, compared with 1.04 trillion stored and 32.6 billion active in K2.

This distinction matters when comparing a mixture-of-experts model with a dense one. Total parameters describe how much specialized capacity the checkpoint can hold. Active parameters better approximate the matrix work used for a token, although they still do not determine latency by themselves. Routing, communication, memory format, batch size, and kernels all affect the cost. K3 stores about 2.7 times as many parameters as K2 and activates about 3.2 times as many. Its design challenge is therefore larger along both axes: the checkpoint is much heavier, and each token also asks more of the machine.

The optimizer and context schedule

K3 applies Per-Head Muon to the query, key, and value projection matrices, preserves K2's weight clipping, and replaces the earlier auxiliary MoE balancing loss with Quantile Balancing. The learning rate follows cosine decay after a one-percent linear warmup, with weight decay set to 0.1. The report does not give the peak or minimum learning rate, batch size, clipping threshold, number of steps, total tokens, total arithmetic work, hardware count, or wall-clock duration. Context length grows late because attention and activation costs make long sequences expensive. Ordinary pre-training begins at 8K and later reaches 64K. The supervised cold start

Supervised fine-tuning (SFT) gives the base model a common interaction format and enough worked examples to begin agent training. Earlier domain-specialized Kimi models generate complex trajectories. Partial rollouts keep the long tail moving

Agent trajectories vary wildly in length. A batch that waits for its slowest trajectory leaves finished workers idle; a batch that discards unfinished work wastes the most expensive examples. K3 uses partial rollouts. For N prompts and K completions per prompt, the system maintains N × K active trajectories. It pauses an iteration when a fraction λ has finished, queues the unfinished states, and gives them priority in the next iteration. A prompt enters policy optimization only after all of its K responses complete.

  1. 1

    Launch several responses for every prompt and retain their model, tool, cache, and environment state.

  2. 2

    When λ of all responses finish, stop waiting for the longest tail and start the next policy iteration.

  3. 3

    Resume the paused responses first. Their exact sandboxes and cache prefixes survive the boundary between iterations.

  4. 4

    Once every response for one prompt is ready, compute the group reward and make that prompt eligible for optimization.

The price is policy staleness. A trajectory may begin under an older policy and finish after several updates. It is then off-policy: the current model is learning from actions sampled by an earlier version. The team says a per-token regularization penalty discourages large policy changes and keeps this stable. The report does not publish N, K, λ, a staleness limit, the penalty coefficient, or a throughput comparison with synchronous rollouts. The algorithm is clear; its measured benefit is not reported.

Effort is trained as a budget, not a mood

The effort levels are enforced through length-relative penalties. A cold-start model first estimates a baseline budget b0(x) for each problem. A trajectory receives reward −1 when its length exceeds τ times that baseline. On general tasks, length counts thinking tokens. On agent tasks it counts cumulative output, including reasoning and tool-call arguments. Training begins with a large τ for the max-effort teacher, still under an absolute cap, and anneals τ to produce high- and low-effort teachers. The settings vary by domain with human guidance.

This penalty sits beside a competing trend: the capability curves improve as the agents take more steps. K3 is trained to spend extra computation when it earns reward and to stop when the trajectory becomes wasteful. The report does not publish the τ values, the distribution of learned lengths, or quality-versus-budget curves, so we cannot inspect how sharply the three effort modes separate.

Many agent tasks have deterministic or programmatic verifiers. Writing and other non-verifiable work uses an Agentic Generative Reward Model. The grader reads the output, writes a rubric, scores each candidate against it, and records the scores in a scratch area. Candidates compete through tournament-style binary comparisons. A response longer than σ times the cold-start verbosity loses automatically. This gives verbosity its own control instead of treating every extra token as evidence of better work. The σ value and reward-model validation are not disclosed. §4.1.2, p. 13 ↗

Distillation consolidates behavior

Nine separate deployment models would be costly and awkward. MOPD samples a domain and effort pair, rolls out the unified student, and scores each sampled token with the matching teacher. The reward is the teacher-to-student log-probability ratio. It is treated as a fixed score, so differentiation does not flow back through its calculation, and it is clipped to a symmetric interval. The method distills on the student's own trajectories, so the teachers advise it on the states it reaches instead of only replaying a fixed teacher dataset. A denser top-k objective, which would transfer several token probabilities at each position, showed no clear improvement in convergence or final performance according to the report. No curves, clipping value, teacher-sampling weights, compute total, retention breakdown, or baseline appear in the paper. The final model is evidence that consolidation can work at this scale; the report does not let us quantify how well each specialist survived the merge. §4.1.3, pp. 13–14 ↗

The environments teach the agent what work looks like

Much of K3's agent behavior comes from the worlds built around the policy. The team creates tools, websites, repositories, office applications, machines, hidden tests, and reward rules that allow a trajectory to last for hours while still producing a checkable result.

One environment can reproduce several agent interfaces

Agent policies can overfit to the wrapper around a task. Tool names, message templates, available memories, context-management rules, subagent APIs, and even error formats become shortcuts. K3's white-box environment makes those pieces configurable. It can reproduce the interaction style of Kimi Code, Claude Code, Codex, OpenClaw, and Hermes, or assemble a new setup from the same parts.

Changing tool names and message formats should not break the agent. A model that has seen several schemas has a better chance of recognizing a new one as another way to inspect files, search the web, or run code. The report gives no cross-wrapper ablation, so the benefit is a design argument rather than a measured result. The interface layer still deserves attention because it changes what the policy observes and which actions it can take. §4.2.1, pp. 14–15 ↗

A knowledge graph becomes a task generator

Broad seed topics are recursively expanded into a directed acyclic graph. An agent runs several web searches for each node, splits coarse ideas into finer ones, reuses an existing node when two branches reach the same concept, and stops when it judges a node atomic. The direction of an edge records movement from coarse to fine. Nodes at several levels can then supply retrieval queries, source bundles, and task prompts.

This mechanism produces related problems without copying one template at a time. A broad banking node can lead to financial statements, ratios, sector rules, and source-specific questions. A visual-science node can lead to plots, diagrams, measurements, and small computation tasks. Reusing equivalent nodes also connects areas that would otherwise grow as isolated trees.

KDA trades a growing cache for a serial state update

Full attention offers parallel work across a prompt but stores keys and values that grow with its length. KDA stores a fixed-size state for each head, which cuts cache growth and transfer volume. Its recurrence introduces a different problem: token t depends on the state from token t − 1. A literal implementation would march through the prompt serially and leave much of the GPU idle.

FlashKDA breaks the prompt into chunks. Tokens inside one chunk can be processed in parallel; only the small summary passed from one chunk to the next remains sequential. The implementation uses CUTLASS, NVIDIA's building blocks for GPU matrix operations, and changes its work schedule for short, long, small-batch, and large-batch inputs. The report explains how operations overlap and reuse memory, but gives no throughput comparison. §5.1.1, pp. 17–18 ↗

Training a 2.78T sparse model takes several kinds of parallelism

The model is too large for one GPU. Training therefore divides layers, experts, optimizer memory, gradients, and long sequences across many devices. Each division attacks a different limit: how much a GPU can store, how much work it can perform, or how much data workers must exchange.

The distribution names used in the report

Pipeline parallelism gives consecutive groups of layers to different workers. Expert parallelism spreads the 896 experts across workers. Context parallelism divides a long token sequence. ZeRO-1 shards optimizer memory, while Pipeline ZeRO-2 also limits which gradient pieces stay resident. Virtual pipeline stages interleave smaller layer groups to reduce waiting time.

These partitions interact. Routing may send many tokens to an expert located on another rank. Pipeline stages create bubbles, idle time while one stage waits for another. Sharded states have to arrive before their operation runs. Vision adds a separate encoder whose patch tokens and activations occupy memory. Activation memory becomes a scheduled resource

A unified activation manager chooses whether an intermediate tensor stays on the GPU, is recomputed, is quantized, is moved to host memory, or is sent to remote memory. Most saved activations use a blockwise 8-bit format before offload. The system overlaps transfers with forward and backward computation and allocates buffers through a common lifetime plan. Pipeline ZeRO-2 further limits resident gradients, and reference weights for RL stream through two reusable gradient slots: one slot serves the current virtual pipeline chunk while the other prefetches the next. MoonViT-V2's image patches are sharded, and its encoder work is placed inside language-model pipeline bubbles. The report explains the schedules but gives no memory totals, transfer bandwidths, utilization, or end-to-end pre-training throughput. §§5.2.2–5.2.3, pp. 20–21 ↗

Million-token RL preserves unfinished work

The RL cluster is co-located so one experiment fits within a few hundred GPUs. Policy training, rollout generation, reference-model work, and cache storage share that footprint. Partial rollouts cross iteration boundaries, so the system retains their prefix state in an external KV pool backed by CPU DRAM. Adaptive throttling slows generation before cache pressure becomes an out-of-memory failure.

Keeping the state is especially valuable at one million tokens. Recomputing a paused prefix every time the policy resumes would erase the throughput gained by partial rollouts. The pool turns an unfinished trajectory into a resumable job whose previous attention work remains available. The report does not publish hit rates, DRAM capacity, transfer cost, or a utilization comparison with a non-persistent design. §5.3.1, pp. 21–22 ↗

AgentENV preserves the sandbox while the model thinks

Early container-based experiments caused kernel panics and deadlocks when agents explored aggressive system operations. AgentENV instead runs Firecracker microVMs: small virtual machines with their own guest operating-system kernel. The stronger isolation lets tasks mount disks, start containers, or even launch nested virtual machines without giving the agent control of the host kernel.

Incremental checkpointing saves only pages dirtied since the previous checkpoint. The report measures checkpoint latency as low as 133 milliseconds and resume latency as low as 49 milliseconds. A paused sandbox uses no CPU or memory, which matters because waiting for model inference can occupy up to 98 percent of its lifetime. Forking creates a side-effect- free copy for reward judging, while snapshots provide recovery points.

The team also changed image storage, virtual-disk input and output, memory sharing, and direct transfer between machines. Together those changes produce subsecond launches at scale and up to 6.5× memory overcommit in the reported workloads. Across K3 training and evaluation, the system created 51,219,741 sandboxes from 1,505,678 images. These are among the report's most concrete operational numbers. They describe the environment fleet, not the number of unique RL tasks or successful trajectories. §5.3.2, p. 22 ↗

The storage mechanisms behind those numbers

OverlayBD shares read-only layers between virtual-disk images. The custom ublk driver handles block storage in user space. Copy-on-write memory lets sandboxes share pages until one modifies a page, and page-cache changes improve reuse of recently read file data. Peer-to-peer transport moves state directly between machines.

Serving must restore two kinds of memory together

A K3 block has three KDA layers and one MLA layer. MLA keeps a per-token cache that grows with the prompt. KDA keeps one large fixed state per request. A reusable prefix needs both caches at the same token boundary. The serving engine packs them into one paged pool so allocation, reference counting, transfer, and eviction use a shared implementation even though the page contents have different types.

KDA checkpoints are too large to store at every token. Physical cache blocks therefore span 1,024 to 6,144 tokens. If prefix matching used only those coarse blocks, a shorter shared prefix could not hit. The engine separates allocation granularity from hash granularity: MLA prefixes are hashed at 512-token boundaries inside a physical page, and sparse KDA state checkpoints are retained at eligible hash endpoints, often conversation turns.

Lookup first finds the longest MLA hash match, then requires a compatible checkpoint in every KDA cache group. Shared blocks are pinned before private allocation, freshly copied pages cannot be matched before their GPU copy completes, and eviction of one KDA group invalidates sibling checkpoints atomically. Those rules keep the two cache families at the same declared token boundary under concurrent scheduling. §5.4.1 and Figure 12, pp. 22–24 ↗

Speculative decoding replays small projections

KDA decoding updates its recurrent state in place. If speculative verification rejects a drafted suffix, the state has already advanced beyond the accepted prefix. Saving one full state per draft position would multiply the dominant memory traffic. The K3 kernel caches the much smaller projected inputs for each draft token, replays the accepted ones on chip, and writes back only the verified and bonus-token states.

The serving kernels combine several small operations so intermediate values need not make separate trips through memory. During prefill (the first pass over the existing prompt), AttnRes spreads activations across sequence workers. During token-by-token decoding, it performs some depth work on a second GPU stream. LatentMoE overlaps worker communication with expert computation and begins its all-gather in the final stage of a matrix multiplication. The report explains these choices but gives no final acceptance-rate, latency, or speedup table for them. §5.4.2, pp. 24–25 ↗

A cached prefix determines where a long request runs

A typical million-token coding request is described as carrying a 400K cached prefix and only 4K new tokens. The scheduler sends the request to the cluster holding that prefix. Consistent hashing, a deterministic rule that moves only part of the traffic when machines change, assigns a primary and a secondary cluster. The secondary accepts the session after a failure and recomputes its cache, spreading failover work across the fleet.

Traffic ranges from requests under 2K tokens to requests near one million, roughly three orders of magnitude in per-request cost. Admission control gives different request classes separate resource budgets so a burst of long prompts cannot consume the entire fleet and delay every short request. This is a production policy, not an architecture theorem. Its effectiveness would require latency distributions, cache-hit rates, queue data, and failure traces, none of which appear in the report. §5.4.3, p. 25 ↗

Where K3 is strong, and where it still trails

The evaluation picture is more interesting than a single rank. K3 leads several coding, search, office, document, and web-development tests. It remains behind the best proprietary models on parts of research reasoning, difficult computer use, and some long-form knowledge work. How to read the scores

benchmark
A fixed set of tasks together with a scoring rule. Different benchmarks measure different things, so their numbers are not directly comparable.
temperature
A sampling control. At 1 the model uses its stated token probabilities; lower values concentrate more heavily on likely tokens.
F1
A score that balances how many returned answers are correct with how many of the correct answers were found.
pass@k
Whether at least one of k generated attempts passes the task's checker.
Elo
A relative rating updated from pairwise wins and losses; it is not a percentage correct.
error bar
An estimate of uncertainty from sampling or repeated runs. A table without one makes tiny score gaps hard to interpret.

Read the benchmark conditions before the scores

Every K3 result in the main table uses max reasoning effort and temperature 1. Single-step reasoning and vision tasks use top-p 0.95: sampling keeps the smallest set of likely tokens whose probabilities add to at least 95 percent. Claude Fable 5 may fall back to another model, and GPT-5.6 Sol may apply cyberguards. These policies change both capability and cost.

MiniTriton spans a compiler stack

K3 built MiniTriton, a compact compiler for GPU tensor programs. A small Python language describes calculations on rectangular tiles of data. The compiler turns that language into an intermediate representation, applies rewriting passes, generates GPU instructions, and runs them through a CUDA runtime. A tensor library above it can execute operations immediately or compile them first; it also supplies differentiation, neural-network modules, distributed training, sparse operations, and visualization. The project therefore spans the whole route from user code to a training loop, not one isolated kernel.

On an NVIDIA L20, the report says MiniTriton's geometric mean beats ordinary immediate PyTorch execution and torch.compile across its core suite. The largest from-scratch matrix multiplication reaches about 90 percent of the fastest rate measured on that machine and approaches NVIDIA's tuned matrix library. Its KDA prefill kernel beats the matched Triton reference. A small GPT trains end to end with a loss curve close to PyTorch; full-model gradient differences stay within 10−4 of Torch autograd when both are compared with an FP64 reference.

This case has public code, which makes it more inspectable than a screenshot of an agent conversation. The paper still does not provide a blinded comparison of generated compiler quality or isolate which parts humans repaired. It supplies roofline plots, convergence curves, and numerical checks for the finished artifact. Figure 15 and §7, pp. 33–34 ↗

A 48-hour chip-design run

In another autonomous run, K3 builds an inference-chip prototype for a small version of its own architecture. The design includes hybrid KDA and MLA, Block AttnRes with a block size of two, sigmoid MoE routing with one shared expert, and four-bit integer weights that share quantization settings in groups of 128. Kimi Code runs for 48 hours using open electronic-design-automation tools and Nangate45, a library of reusable logic cells.

The resulting design meets a 4 mm² analytical area budget, closes timing at 100 MHz, and reports more than 8,700 tokens per second in RTL simulation. It contains 1.46 million standard cells, 0.277 MiB of on-chip static memory, and a four-bit multiply-and-add array that converts values back to a wider format as part of the operation. These are pre-silicon numbers from an RTL flow, not measured performance from fabricated hardware. The source release makes the artifact available for a deeper engineering audit.

Scientific code joins retrieval and implementation

For an astrophysics task about I–Love–Q universal relations, K3 reviews more than twenty papers, cross-checks their results, implements a numerical pipeline, evaluates over 300 equations of state, finds inconsistencies in published formulas, writes more than 3,000 lines of Python, and produces an interactive HTML dashboard. The report gives a runtime of about two hours and estimates one to two weeks for an experienced researcher.

The time comparison is anecdotal because no matched human study is described. The output profile is still revealing. A successful trajectory has to keep citations, formulas, numerical code, data products, and a user-facing explanation consistent. That combination resembles the search, professional-work, coding, and web environments used during RL.

Research websites and concurrent subagents

One Kimi Work case produces an interactive history of 42 years of the AI-ASIC industry. It goes through more than 120 revisions, reads 87 quarterly reports and 99 original PDFs totaling over 11,000 pages, runs more than 2,800 web searches, and issues more than 1,100 terminal queries. Another case analyzes 391 gravitational-wave events from GWTC-5 with more than twenty concurrent subagents, then produces seven scientific visualizations, two summary tables, and a synthesis of more than ten papers.

Large counts do not prove the conclusions are correct. They show why context management, source tracking, tool reliability, and subagent coordination become first-class model capabilities. A human audit would need to inspect the cited reports, generated tables, calculations, and revision history.

The team estimates one to two days for an experienced editor to make a comparable short video.

The report gives no numerical quality test for the video. What it does show is the scale of task the team wants K3 to handle: hours of tool use ending in a finished artifact. These are selected demonstrations, not an average success rate.
