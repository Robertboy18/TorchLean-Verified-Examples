Taking autoformalization into ML

Mathematicians have been putting research papers into Lean for years, and the Liquid Tensor Experiment and the Polynomial Freiman–Ruzsa project showed how people could work through substantial mathematics together (writing the definitions and filling in the arguments until Lean could check the proofs). I want us to do that for machine-learning papers too.

Now AI is helping with the translation itself. In September 2026, Anthropic reported a complete Lean formalization of Fermat's Last Theorem, building in part on Kevin Buzzard's community project. This is what people mean by autoformalization: taking mathematics written for people and producing definitions and proofs a proof assistant can check. Seeing this happen for research mathematics makes me want to push further with ML :)

There's also recent work around the Riemann hypothesis. OpenAI's Lean formalization of the quasi-Riemann hypothesis describes a zero-free region \(\operatorname{Re}(s)>7/8\) for the Riemann zeta function (the Riemann hypothesis itself would put every nontrivial zero on \(\operatorname{Re}(s)=1/2\), so the zero-free-region result is a different statement). What interests me here is the practice of publishing the mathematical argument together with a formal statement that you can open and inspect yourself.

A model report contains equations we can translate into tensor functions: how a recurrent state changes, how attention reads a cache, how a router chooses experts, and how their outputs are combined. Then we can ask whether an implementation computes those equations and prove properties that matter when we use it. Because those definitions can take different weights and dimensions, the proofs can cover a whole family of models. I'd call this model autoformalization. AI could help translate the equations and find proofs while Lean checks the arguments, but in this post I want us to work through the calculations ourselves, starting with small examples before the full tensor equations.

We can write the tensor computations and their mathematical properties together, and FloatLib supplies arithmetic definitions and rounding theory for the next question: what changes when we calculate with finite precision? That matters in ML, where the choice of precision and accumulation order can change a model's output. I want those choices to be part of the formalization, close to the equations that use them.

I think K3 is a good place to start because several of its architectural choices interact. Kimi Delta Attention (KDA) updates a recurrent memory, while Multi-head Latent Attention (MLA) looks back at individual cached tokens. It also retrieves summaries from earlier layers and sends each token through selected groups of weights (called experts), and an image goes through a vision encoder before it joins the language model. To formalize the model, we have to understand how those calculations share their inputs and state. Figure 2 and §2, pp. 3–4 ↗

That leads to concrete questions. Does splitting a sequence into two chunks preserve the output when we carry the state between them? Does the graph of tensor operations compute the same function as the paper equation? How large can a capped activation become? We can answer these with theorems about the definitions, and later ask how rounding changes the calculations.

In the Kimi team's introduction to K3, the architecture serves a larger ambition: a model that can keep working through long coding and research tasks. I like that they explain the memory and routing choices behind it, because those choices also give us mathematical questions we can settle. If a serving system pauses a calculation, resumes from a cache, or changes how it groups tokens, you'd want to know which changes preserve the function and which change its numerical behavior.

I'll start with the transformer calculations that K3 builds on, then work through its memory, attention, experts, and vision model, keeping the report beside the explanation. After that, the training and evaluation sections give us another part of the story: how the authors used those mechanisms and what they measured.

Start with a transformer

At each generation step, a language model looks at the preceding context and assigns probabilities to the next token. K3 does this with 93 layers, 2.78 trillion parameters, and a million-token context, but a plain transformer gives us a good starting point for understanding the calculations that K3 changes.

  1. 1

    Tokenize. First the text gets split into vocabulary pieces called tokens (roughly word fragments), and each gets an integer ID. "unhappy" might become two tokens: "un" and "happy." Everything downstream works with these integer IDs.

  2. 2

    Embed. Each token ID selects a learned vector from a lookup table. A vector is just an ordered list of numerical coordinates (K3 uses 7,168 of them per token), and training adjusts those numbers so the later layers can use them when predicting the next token. A concept need not live in one particular coordinate.

  3. 3

    Compute match scores. Three learned matrices project each token's vector into a query, a key, and a value. A dot product compares the current query with each key, and those scores determine how much each value contributes to the attention output.

  4. 4

    Mask the future. When predicting the next token, a position can only look at itself and earlier tokens, never later ones. This causal mask leaves future positions out of the weighted sum, and the usual attention notation writes their scores as negative infinity.

  5. 5

    Weight the answers. Softmax converts all the match scores for one token into nonnegative weights that sum to one (in the real-valued equation). Weights of 0.4 and 0.3, for example, multiply their value vectors by those amounts, and adding the weighted values gives the attention output.

  6. 6

    Update and continue. A residual connection adds the old vector back to the attention output. Then a feed-forward network processes that updated vector, and another residual addition carries the result to the next layer. So the residual path lets a block add an update to the vector it already has rather than replace it entirely.

Steps three through five fit into one line of the standard attention equation, where capital letters stand for tables with one row per token: holds the queries, the keys, and the values.

  1. takes every allowed query–key dot product. A dot product multiplies matching coordinates and sums them, giving one match score per position pair.

If the coordinate products are independent and each has variance one, their sum has variance , and this division brings it back to one (otherwise large score differences can make softmax concentrate heavily on one position). That variance argument is why people scale this way, but it isn't a law that every wider learned key must produce a larger score.

  4. Multiplying by at the end forms a weighted combination of the value vectors from all allowed positions.

Negative infinity here is shorthand for excluding a position, because a finite negative score still has a positive exponential over the real numbers, however small it is. So the real-valued hard-mask definitions give forbidden positions exactly zero weight. If a numerical implementation uses a finite sentinel instead, you have to check that sentinel against the masking behavior you intend.

Conventional multi-head attention runs this calculation across many attention heads in parallel. Each head uses its own separate query, key, and value projection matrices, so different heads can learn to pay attention to different things: one might track syntactic structure, another semantic role, another pronoun reference. K3 uses 96 heads. Their outputs get concatenated and projected back to the model width. A conventional cache with separate keys and values for every head multiplies its payload by the head count, while K3's MLA cache keeps a shared latent representation instead (we'll count that smaller representation separately).

Dot products alone don't encode where a token occurs in the sequence. Many transformers add positional information for that, and rotary positional embeddings (RoPE), for example, rotate query and key coordinates according to position. K3 uses NoPE MLA, whose shared-key coordinates stay unrotated, and its KDA layers carry order through sequential state updates (change the order of the inputs and you change which state each update receives).

Every block computes , and the representation going into the next block is . If is small, the original vector survives nearly unchanged. Over many layers the residual stream accumulates the blocks’ contributions, so a later block receives information written at several earlier depths in one sum, and K3’s AttnRes keeps those earlier block sums available for separate retrieval.

Most of the model's parameters live in the feed-forward half of each block. It takes the current hidden vector, projects it up to a wider hidden space, applies a nonlinearity, and projects back. In K3 this becomes a mixture-of-experts layer rather than one dense network, and each token only activates a small fraction of the available capacity. But the basic pattern is the same.

Training processes many token positions in parallel, but inference is different: the model generates one token, appends it, and runs again. Keys and values from previous steps don't change, so implementations save them in a KV cache that grows by one entry per token per attention layer. That's the trade-off the original transformer design made. Instead of compressing history into a fixed recurrent state (like an LSTM would), it keeps the full history directly accessible, and storing that history costs more as the context grows. K3's hybrid attention is one way to manage the growing cache.

The Attention Is All You Need paper from 2017 made this pattern work at scale. Later decoder models have changed normalization, positional encodings, activations, and attention layout, but the alternating rhythm (attention to mix between positions, then feed-forward to transform within one position, then residual addition, then the next layer) stayed recognizable all the way through to K3.

The cost of a longer, larger model

We can make a transformer larger by adding layers, widening its vectors, or using longer sequences. Longer sequences enlarge the attention cache, and more experts mean more weights to store even when each token uses only a few. Let's look at how K3 handles these costs.

Attention and a growing cache

For a full causal sequence of length , one attention layer has permitted query–key pairs. Efficient kernels can avoid storing the full score matrix, but they don't turn quadratic attention into a constant-size recurrence, and during generation the KV cache still grows by one entry per new token in every full-attention layer.

So how do you shrink that cost? Models do it in two broad ways: store less information for each previous token, or replace the growing table with a fixed state that is updated after every token. K3 uses both. Multi-head Latent Attention (MLA) keeps one compressed entry for each earlier token, so a layer can still look back at individual positions. Kimi Delta Attention (KDA) keeps a fixed-size recurrent matrix instead, so its memory does not grow with sequence length.

More parameters, more matrix work

In a transformer, the feed-forward network often owns most of the parameters. Sparse mixture-of-experts models keep many feed-forward networks but route each token through only a few, and the Switch Transformer demonstrated this at trillion-parameter scale. Only the selected experts compute an output for a token, but all the expert weights still need storage (and routing adds load-balancing and communication costs on top).

One residual stream across many layers

A conventional residual stack carries a single running sum. By layer ninety, that vector contains contributions from every earlier block, so what if the current layer wants one particular old representation? It can't pick that out directly. It receives the sum. Attention Residuals changes the depth path: block summaries remain visible and the current layer retrieves a weighted mixture. K3 stores summaries of groups of layers, rather than a separate summary for every layer.

Bringing images into the sequence

A vision transformer turns an image or video into patch tokens. A multimodal language model must decide where those tokens enter, how their feature width matches the language backbone, and whether training treats visual and text examples as one sequence from the beginning. In my formalization I have to pin down the projection to the language backbone's width and where the visual tokens enter the sequence.

Kimi's earlier Kimi Linear work developed Kimi Delta Attention as a gated delta-rule recurrence and paired mostly recurrent layers with occasional full attention. K3 brings that hybrid into a much larger system, adds depth retrieval and a latent expert space, and trains the result as a native multimodal model.

K3's architectural choices

KDA and MLA split the sequence problem: KDA carries a fixed-size summary forward, while periodic MLA layers can still inspect individual cached tokens. AttnRes retrieves earlier summaries across depth, and Stable LatentMoE expands capacity across width without running every expert. MoonViT-V2 turns images and video into vectors the language backbone can consume.

Put together, that's a model with 2.78 trillion parameters that activates 104 billion of them for each token, accepts text, images, and video, and supports a context window of 1,048,576 tokens. And Moonshot released the weights! That matters to me, because it gives the formalization a concrete object to aim at instead of an architecture reconstructed from an API description.

Scalar types and tensor shapes

          
The Greek letter α (alpha) names the scalar type. Most proofs here use
            real numbers, while an executable calculation can use a finite format such as a 16-bit float.
            Definitions that leave α open specify the operations they need, so we can
            reuse their tensor layout with different arithmetic, but a theorem about real arithmetic
            still needs a refinement argument before it describes rounded execution.


          
A type like Tensor α [4, 2] means a tensor of α-values
            with four rows and two columns. That shape [4, 2] is right there in the type,
            not hidden in a runtime assertion, so Lean checks these dimensions when it typechecks
            the program and connecting incompatible shapes produces a type error before the
            calculation runs.


          
Here's a small shape puzzle before the larger equations: how many values does a tensor with no axes hold? One!
            Tensor α [] holds a single scalar (no axes doesn't mean no values), while
            Tensor α [0] is an empty vector, because its one axis has length zero.
            Since the number of entries is the product of the axis lengths, and the product of no lengths
            is one, a reduction can return a scalar tensor without introducing a
            different container type.


          
Indices, tensors, and growing caches

          
Fin n pairs a natural number with evidence that it's less than
            n, so an expert ID of type Fin 896 ranges from 0 to

Definitions and theorems

          
A structure bundles named fields. A model record can hold weight
            matrices, a cache record can hold state, and a probability record can pair a number with
            evidence that it's positive. To see how those fields affect the model, follow the
            functions that consume them.


          
A def defines a function or value. It consumes structures and produces
            new ones (or produces tensors). This is where the actual computation happens. A
            theorem makes a claim about what a def returns: after
            theorem, everything up to := by is the statement being
            proved, and the lines after by are tactic commands that Lean uses to build a
            proof term that its kernel verifies. If you see simp or ring
            or linarith, those tactics simplify expressions, normalize polynomial
            identities, or solve linear inequalities, and Lean checks the proof terms they produce.

How K3 was pre-trained

The data mixture starts multimodal

        
The text corpus is organized around web text, code, mathematics, and knowledge, and the
          pipeline that builds it combines rules, learned quality classifiers, and deduplication.
          Sampling rates for the domains come from ablations on smaller models. So you get the
          process that picked the rates, but not the rates themselves.


        
Before base-model pre-training, the team rewrites knowledge and mathematics sources,
          with prompts that ask for different styles and viewpoints and long sources rewritten
          chunk by chunk. A later fidelity check tries to keep the facts intact. So the model
          learns from transformed versions of some of its source material, as part of its base
          corpus. I think that fidelity check matters, because a rewrite can change a formula or a
          factual detail even when the new prose sounds convincing.


        
On the vision side, the corpus covers captions, documents with interleaved images and
          text, OCR, perception, video, and visual coding. Localization examples give coordinates
          two ways (absolute, and normalized to the unit square). Programmatic examples pair code
          with rendered outputs such as SVG images, webpages, games, 3D assets, and CAD drawings,
          which lets the model learn from code alongside the image or application it produces. You'll
          see related tasks again in the web-development and visual-agent evaluations.
          §3.1, p. 10 ↗


        
Joint vision-language training

        
MoonViT-V2 and the language model train together from the very first step, under the
          same next-token objective. Visual features are resized to the language embedding width and
          interleaved with text tokens, so the language loss also changes the vision encoder (the
          report calls this native multimodal training). A wrong answer to an image
          question, for example, can change both the features extracted from the image and the
          language model that uses them, and the two parts learn to work together under that one
          objective.


        

        
The optimizer and context schedule

        
Per-Head Muon updates the query, key, and value projection matrices in separate head
          blocks. K3 also keeps K2’s weight clipping, and it sets the expert selection biases with
          Quantile Balancing, in place of the fixed-step bias update of earlier auxiliary-loss-free
          routing. Learning rate rises during a one-percent linear warmup and then follows cosine
          decay, with weight decay at 0.1. That's enough to describe the update schedule, but you couldn't
          replay the run from it, since the peak learning rate, batch size, clipping threshold, and
          total token budget aren't specified.


        
Why does context length grow so late? Because attention and activation costs make long
          sequences expensive. Ordinary pre-training begins at 8K and later reaches 64K, and only during
          cooldown does the model advance to 256K and then one million tokens. According to the
          authors, these long-context stages are a small fraction of training. For those stages,
          the team upsamples scarce coherent long documents and videos, cleans them with exact
          and fuzzy deduplication (and perceptual hashes for frames), and adds synthetic
          examples that scatter the evidence needed for one answer across several concatenated
          documents and subtasks.


        
KDA uses no explicit positional encoding. Its recurrent decay and gating make the
          order of tokens affect the state, so the team can extend the sequence without
          rescaling rotary positional embeddings (RoPE, a common way to rotate query and key
          coordinates according to token position) or interpolating position indices. Dropping
          RoPE removes one engineering obstacle, but I still want to know whether the state
          keeps the information a long-context task requires. We'll see retrieval benchmarks
          address that question later, under their own evaluation setups.
          §§3.3–3.4, pp. 11–12 ↗


        
I find it useful to think about the shared training objective and the late context
          expansion together. K3 first learns from many kinds of input, then spends part of its
          final training on much longer examples. The report is enough to understand that order
          of choices, but you'd need the underlying runs to reproduce what it cost.

Post-training · Report §4.1, pp. 12–14

        
Training nine specialists, then combining them

        
Post-training proceeds in three stages. Supervised trajectories first establish a
          usable agent, then reinforcement learning separates domains and reasoning budgets into
          nine specialist policies, and finally Multi-Teacher On-Policy Distillation brings their
          behavior back into one student.

      

      

        

          
Post-training terms used below

          

            
policy
The model viewed as a rule that assigns probabilities to its next
              token or action.

            
trajectory
One complete attempt: prompt, generated tokens, tool calls,
              observations, and final answer. Producing one is a rollout.

            
reward
A numerical score for the attempt. A verifier may compute it, or
              another model may judge the result.

            
RL
Reinforcement learning: update the policy so actions leading to
              higher expected reward become more likely.

            
distillation
Train one student model to reproduce useful behavior from
              one or more teacher models.

          

        

        
Starting with supervised examples

        
Supervised fine-tuning (SFT) gives the base model a common interaction format and
          enough worked examples to begin agent training. Earlier domain-specialized Kimi models
          generate the complex trajectories, which pass through several verification stages and
          human annotation before anything trains on them. Every conversation uses XTML (the text
          format that serializes messages, tool calls, and tool results for the configurable agent
          wrappers and inference system).


        
These demonstrations are meant to teach the model to adjust reasoning effort, call
          tools precisely, and keep working through long tasks, all before reinforcement
          learning begins. (The report doesn't measure how much each part of this cold start
          contributes.) They also give RL a better starting point, because the model can already
          attempt the interaction that the reward will judge.
          §4.1.1, p. 12 ↗


        
Three domains crossed with three effort levels

        
The RL stage separates capability from computation. Its first axis is the domain, and
          there are three. General-task training covers ordinary experience, vision, reasoning,
          faithfulness, search, and knowledge work. General-agent training covers long-horizon
          assistants, deep research, and paragraph-level writing, while coding-agent training covers
          software engineering, coding experience, kernel work, and web development.


        
The second axis is reasoning effort (low, high, and max), and crossing the two axes
          produces nine teachers. So a low-effort coding policy learns under a tighter budget than a
          max-effort coding policy, and both are distinct from a max-effort general agent.

Training with problem-specific token budgets

        
Effort levels are enforced through length-relative penalties. First a cold-start model
          estimates a baseline budget \(b_0(x)\) for each problem, and a trajectory receives reward
          −1 when its length exceeds τ times that baseline. Length means thinking tokens on general
          tasks and cumulative output on agent tasks (reasoning and tool-call arguments included).
          Training begins with a large τ for the max-effort teacher, still under an absolute cap,
          and anneals τ to produce high- and low-effort teachers, with settings that vary by domain
          under human guidance.


        
This penalty pulls against another trend, since the capability curves improve as the
          agents take more steps. What K3 is trained to do is spend extra computation when it earns
          reward and stop when the trajectory becomes wasteful. To compare the effort modes, I'd
          want task success plotted against tokens spent for each one. Figure 8 only shows the
          broader training trends.


        
Many agent tasks have deterministic or programmatic verifiers. For writing and other
          non-verifiable work, K3 uses an Agentic Generative Reward Model, a grader that reads
          the output, writes a rubric, scores each candidate against it, and records the scores
          in a scratch area. Candidates then compete through tournament-style binary
          comparisons, and a response longer than σ times the cold-start verbosity loses
          automatically. That gives verbosity its own control, instead of treating every extra
          token as evidence of better work. For these tasks I'd worry about the grader as much as
          the policy, because a model can learn to satisfy a judge without making its answer
          more useful.
          §4.1.2, p. 13 ↗


        
Combining the specialists through distillation

        
Nine separate deployment models would be costly and awkward, so how do you fold them
          back into one? For a given domain, MOPD samples an effort level, rolls out the unified student, and scores each sampled token
          with the matching teacher, using the teacher-to-student log-probability ratio as the
          reward. That reward is treated as a fixed score (differentiation doesn't flow back through
          its calculation), and it's clipped to a symmetric interval. I'll write it out in the next
          section, along with its Lean bound.


        
Because the student generates the trajectories, teachers score the states it actually
          reaches during its own attempts. The team also tried a denser top-\(k\) objective that
          transferred several token probabilities at each position, and found no clear improvement
          in convergence or final performance. What you get in practice is one student that can
          switch domains and effort levels without loading a different model. There's no separate
          retention score for each teacher, though, so the final evaluation measures the student as
          a whole, and I can't read off a teacher-by-teacher transfer rate.
          §4.1.3, pp. 13–14 ↗

What four-bit expert weights mean

        
Quantization replaces a high-precision number with one of a small set of coded
          values. MXFP4 gives each expert weight a four-bit code and MXFP8 gives each expert
          activation an eight-bit code, where “MX” means microscaling (32 neighboring values

Tools, tasks, and rewards

        
Each training task specifies what tools the agent can use and how its work is

Training across agent interfaces

K3 creates three different engineering problems at once: KDA has a recurrent state,
          sparse experts must move across a multi-trillion-parameter training cluster, and agent
          trajectories can hold on to a million tokens plus a live computer for hours. This part
          of the report is about how the team allocates memory, distributes expert computation,
          and stores unfinished rollouts.

KDA trades a growing cache for a serial state update

        
Full attention offers parallel work across a prompt, but it stores keys and values
          that grow with the prompt's length. KDA stores a fixed-size state for each head, which
          cuts cache growth and transfer volume. But its recurrence brings a different problem:
          token \(t\) depends on the state from token \(t-1\), so a literal implementation would
          process the prompt serially and leave much of the GPU idle.


        
So how do you keep the GPU busy? FlashKDA breaks the prompt into chunks. Tokens inside one chunk can be processed in
          parallel, and only the small summary passed from one chunk to the next stays
          sequential. It's built on CUTLASS (NVIDIA's building blocks for GPU matrix operations)
          and serves training and prefill, while long prefills and decoding each get a kernel
          designed for their regime. You get an explanation of how the kernels overlap their
          work, but no throughput numbers.
          §5.1.1, pp. 17–18 ↗

Saving, recomputing, and offloading activations

        
Activations are intermediate tensors that later computations may need again, and
          keeping all of them on the GPU consumes memory, while recomputing or moving them costs
          work. So a unified manager plans their lifetimes and chooses which to keep, recompute,
          quantize, move to host memory, or send to remote memory. Most saved activations use a
          blockwise 8-bit format before offload, and a common buffer plan lets the system
          overlap transfers with forward and backward computation across modules.


        
Pipeline ZeRO-2 further limits resident gradients, and reference weights for RL stream
          through two reusable gradient slots: one slot serves the current virtual pipeline chunk
          while the other prefetches the next. MoonViT-V2's image patches are sharded, and its encoder
          work is placed inside language-model pipeline bubbles. Both schedules try to make room
          for the next operation before it needs to run, rather than keeping every saved tensor
          resident for the whole update.
          §§5.2.2–5.2.3 and 5.3.1, pp. 20–22 ↗


        
Million-token RL preserves unfinished work

        
The RL cluster is co-located so one experiment fits within a few hundred GPUs, with
          policy training, rollout generation, reference-model work, and cache storage all
          sharing that footprint. Because partial rollouts cross iteration boundaries, the
          system retains their prefix state in an external KV pool backed by CPU DRAM, and
          adaptive throttling slows generation before cache pressure starts preempting requests.


        
At one million tokens, rebuilding the prefix on every resume would repeat a large
          amount of attention work. Keeping that work in the pool while a trajectory is paused
          lets the next iteration continue from its cached state. How much time does that
          save? It depends on reuse and transfer costs, since keeping a prefix in CPU memory still costs
          storage and a transfer back to the GPU, and the design trades that cost against
          recomputing the prefix. That trade-off isn't measured end to end in the report.
          §5.3.1, pp. 21–22 ↗

Restoring the recurrent state and attention cache together

        
A K3 block has three KDA layers and one MLA layer. MLA keeps a per-token cache that
          grows with the prompt, while KDA keeps one large fixed state per request, and a
          reusable prefix needs both caches at the same token boundary. So the serving engine
          packs them into one paged pool, which lets allocation, reference counting, transfer,
          and eviction use a shared implementation even though the page contents have different
          types.


        
KDA checkpoints are too large to store at every token, so physical cache blocks span
          1,024 to 6,144 tokens. But if prefix matching used only those coarse blocks, a shorter
          shared prefix could never hit. How does a shorter prefix ever hit, then? The engine
          separates allocation granularity from hash granularity: MLA prefixes are hashed at 512-token boundaries
          inside a physical page, and sparse KDA state checkpoints are retained at eligible hash
          endpoints (often conversation turns).


        

        
Lookup first finds the longest MLA hash match, then requires a compatible checkpoint in
          every KDA cache group. Shared blocks are pinned before private allocation, freshly copied
          pages cannot be matched before their GPU copy completes, and eviction of one KDA group
          invalidates sibling checkpoints atomically. Those rules keep the two cache families at the
          same declared token boundary under concurrent scheduling.
          §5.4.1 and Figure 12, pp. 22–24 ↗


        
Speculative decoding retains the projections it needs

        
KDA decoding updates its recurrent state in place. So if speculative verification
          rejects a drafted suffix, the state has already advanced beyond the accepted prefix,
          and saving one full state per draft position would multiply the dominant memory
          traffic. K3's kernel caches the much smaller projected inputs for each draft token,
          replays the accepted ones on chip, and writes back only the verified and bonus-token
          states. I like this trick a lot.


        
Serving kernels combine several small operations so intermediate values don't need
          separate trips through memory. During prefill (the first pass over the
          existing prompt), AttnRes spreads activations across sequence workers, and during
          token-by-token decoding it performs some depth work on a second GPU stream. LatentMoE
          overlaps worker communication with expert computation and begins its all-gather in the
          final stage of a matrix multiplication. Each of these changes tries to keep a useful
          operation running while another waits for data (the report describes the schedules
          without an end-to-end speedup table).
          §5.4.2, pp. 24–25 ↗


        
Placing requests near their cached prefixes

        
A typical million-token coding request is described as carrying a 400K cached prefix
          and only 4K new tokens, so the scheduler sends it to the cluster holding that prefix.
          Consistent hashing (a deterministic rule that moves only part of the traffic when
          machines change) assigns a primary and a secondary cluster. After a failure the
          secondary accepts the session and recomputes its cache, which spreads failover work
          across the fleet.


        
Requests under 2K tokens share the fleet with requests near one million, which puts
          them roughly three orders of magnitude apart in per-request cost! Admission control (which limits
          how much work each request class can admit) gives the classes separate resource
          budgets, so a burst of long prompts has a budget of its own while short requests keep
          theirs. To evaluate this scheduler I'd want to measure how long each class waits
          under mixed traffic, including bursts and failures. The report describes the policy
          without those latency distributions.
          §5.4.3, p. 25 ↗


        
What I think ties these systems choices together is the amount of work a long-lived request
          leaves behind: recurrent states, attention caches, tool processes, and a filesystem.
          Reusing that work takes more than keeping a tensor in memory, because the caches have
          to agree on a token boundary and the sandbox has to resume at the corresponding point
          in the task. That's why so much of this section is about state lifetimes and recovery.

How to read the scores

          

            
benchmark
A fixed set of tasks together with a scoring rule. Different
              benchmarks measure different things, so their numbers are not directly comparable.

            
temperature
A sampling control. At 1 the model uses its stated
              token probabilities, and lower values concentrate more heavily on likely tokens.

            
F1
A score that balances how many returned answers are correct with how
              many of the correct answers were found.

            
pass@\(k\)
Whether at least one of \(k\) generated attempts
              passes the task's checker.

            
Elo
A relative rating updated from pairwise wins and losses. It
              isn't a percentage correct.

            
error bar
An estimate of uncertainty from sampling or repeated runs. A
              table without one makes tiny score gaps hard to interpret.

          

        

        
How the benchmark runs were configured

        
Every K3 result in the main table uses max reasoning effort and temperature 1.
          Single-step tasks (such as GPQA Diamond and vision benchmarks without tools) use top-p
          0.95, meaning sampling keeps the smallest set of likely tokens whose probabilities add
          to at least 95 percent. Agent and coding tasks use top-p 1, which leaves the full
          vocabulary available. Proprietary baselines also run at their highest listed effort,
          except GPT-5.5 at xhigh. Claude Fable 5 may fall back to another model and GPT-5.6 Sol
          may apply cyberguards, and those policies change both capability and cost.


        
Coding scores may use Kimi Code, Claude Code, or Codex, and Terminal-Bench reports
          the best score obtained across the available execution setups for each model. DeepSWE
          lists 67.5 in the comparison table, while the official mini-SWE-agent result is 67.3.
          SWE-Marathon uses an H20-calibrated pre-release branch dated July 9, 2026, and Fable
          falls back on 35 percent of those tasks. All of these choices are disclosed, which I
          like. They still make small gaps poor evidence of an intrinsic model ordering.


        
BrowseComp uses context compaction at 300K tokens and reaches 91.2, and with the raw
          one-million-token window and no context management K3 scores 90.4. MCP-Atlas and
          AutomationBench use public subsets. WorldVQA required prompt changes to force answers
          after several models refused. Most vision scores average three runs (ZeroBench uses
          five), but the table gives no confidence intervals. Several entries also come directly

My read of the results

          
K3's clearest strengths are coding, web search, document work, visual tool use, and
            web development, and the open checkpoint and detailed report make those results
            easier to inspect. The scores don't put K3 first overall, though. Fable 5 and
            GPT-5.6 Sol still lead in the report, and hard research reasoning, desktop use, and
            some professional tasks expose real gaps. Several headline results are also
            internal, use different agent wrappers, or omit uncertainty. The released weights
            let others investigate the model, but reproducing its internal evaluations also
            needs the tasks and graders.

How to read the engineering numbers

          

            
latency
The time required to finish one operation. Lower is better.

            
throughput
How much work finishes per second. Higher is better.

            
TFLOPS
Trillions of floating-point arithmetic operations per second.

            
compiler
A program that translates a higher-level language into
              instructions a machine can execute.

            
RTL
Register-transfer-level code: a description of how data moves
              through digital hardware each clock cycle.

            
pre-silicon
Measured in design tools or simulation before a physical chip
              has been fabricated.

          

        

        
Up to twenty-four hours of kernel optimization

        
Each model receives an identically configured sandbox and up to 24 hours per task to
          profile, rewrite, and benchmark one of four kernels: AttnRes, DeepSeek Sparse
          Attention, KDA, and MLA with head dimension 512. The machines include an NVIDIA Hopper
          GPU and a second vendor's general-purpose GPU, so the agent can iterate against real
          timing results instead of submitting one code sample for static inspection.


        
K3 cuts AttnRes latency from 283.6 milliseconds to 114.4 milliseconds. It reduces DSA
          runtime by 55.1 percent and KDA runtime by 73.6 percent, and its MLA implementation reaches
          more than half of the measured peak TFLOPS. Across the four tasks, the report says K3
          matches Fable 5 with fallback and exceeds Opus 4.8, Sol, and GPT-5.5. Figure 14 plots the
          AttnRes improvement across active hours, which I find useful, because you can see the
          gains continue after the first working kernel rather than only the final point.

MiniTriton: building a GPU compiler

        
K3 built MiniTriton, a compact compiler for GPU tensor programs. You describe
          calculations on rectangular tiles of data in a small Python language, and the compiler
          turns that language into an intermediate representation, applies rewriting passes,
          generates GPU instructions, and runs them through a CUDA runtime. On top of it sits a
          tensor library that can execute operations immediately or compile them first, and it
          also supplies differentiation, neural-network modules, distributed training, sparse
          operations, and visualization. So the project spans the whole route from user code to
          a training loop, well beyond one isolated kernel.


        
On an NVIDIA L20, the report says MiniTriton's geometric mean beats ordinary
          immediate PyTorch execution and torch.compile across its core suite. Its
          largest from-scratch matrix multiplication reaches about 90 percent of the fastest
          rate measured on that machine and approaches NVIDIA's tuned matrix library, and its
          KDA prefill kernel beats the matched Triton reference. A small GPT trains end to end
          with a loss curve close to PyTorch, and when both are compared with an FP64 reference,
          full-model gradient differences stay within 10−4 of Torch autograd.


        
I like that this case has public code, which already makes it more inspectable than a screenshot
          of an agent conversation. But the paper doesn't provide a blinded comparison of
          generated compiler quality or isolate which parts humans repaired. What it does supply
          is roofline plots, convergence curves, and numerical checks for the finished artifact.
          Figure 15 and §7, pp. 33–34 ↗


        
A 48-hour chip-design run

        
In another autonomous run, K3 builds an inference-chip prototype for a small version
          of its own architecture. Its design includes hybrid KDA and MLA, Block AttnRes with a
          block size of two, sigmoid MoE routing with one shared expert, and four-bit integer
          weights that share quantization settings in groups of 128. Kimi Code runs for 48 hours
          using open electronic-design-automation tools and Nangate45 (a library of reusable
          logic cells).


        
The resulting design meets a 4 mm² analytical area budget, closes timing at 100 MHz,
          and reports more than 8,700 tokens per second in RTL simulation. It contains 1.46
          million standard cells, 0.277 MiB of on-chip static memory, and a four-bit
          multiply-and-add array that converts values back to a wider format as part of the
          operation. These are pre-silicon numbers from an RTL flow and not measured performance
          from fabricated hardware, but the source release makes the artifact available for a
          deeper engineering audit.


        
Implementing an astrophysics calculation

        
For an astrophysics task about I–Love–Q universal relations, K3 reviews more than
          twenty papers, cross-checks their results, implements a numerical pipeline, evaluates
          over 300 equations of state, finds inconsistencies in published formulas, writes more
          than 3,000 lines of Python, and produces an interactive HTML dashboard. By the
          report's count that took about two hours, against an estimated one to two weeks for an
          experienced researcher.


        
I'd treat that time comparison as anecdotal, since no matched human study is described. Still,
          a successful trajectory has to keep citations, formulas, numerical code, data
          products, and a user-facing explanation consistent, and that combination resembles the
          search, professional-work, coding, and web environments used during RL.


        
Research with parallel agents

        
One Kimi Work case produces an interactive history of 42 years of the AI-ASIC industry.
          It goes through more than 120 revisions, reads 87 quarterly reports and 99 original PDFs
          totaling over 11,000 pages, runs more than 2,800 web searches, and issues more than 1,100
          terminal queries. Another case analyzes 391 gravitational-wave events from GWTC-5 with
          more than twenty concurrent subagents, then produces seven scientific visualizations, two
          summary tables, and a synthesis of more than ten papers.


        
Each trajectory has to keep its sources and calculations consistent through many tool
          calls and revisions, and subagents add another coordination problem, because their
          outputs must agree on the data and definitions they share. If you wanted to check the
          finished research, you'd have to follow the cited reports into the tables and
          calculations, then inspect the revision history for unresolved discrepancies.


        
Video editing and motion design

        
K3 creates a motion-graphics explanation of its own architecture in the style of a
          popular mathematics video channel, and edits a teaser from 56 source clips. That work
          includes clip selection, motion-matched cuts, beat-level synchronization, audio
          processing, and several revisions, and the team estimates one to two days for an
          experienced editor to make a comparable short video.


        
There's no numerical quality test for the video. What the report does show is the
          scale of task the team wants K3 to handle: hours of tool use ending in a finished
          artifact.

What the current proofs cover

      
The sequence result is one I especially wanted.
        LanguageModel.run_eq_logits proves that processing embeddings token by
        token gives exactly the public model's full-sequence logits. run_append
        comes from the same causal-scan structure: split the input at any position and every
        logit and the final decoder state are preserved, provided the second chunk resumes from
        the first chunk's state. These are equalities over the real-valued model (deterministic
        expert routing included) for every sequence length and parameter value, and each one
        covers every input its statement admits.

      
The packed graph has its own composed theorem, from token lookup through the decoder to
        vocabulary logits, under the stated dimension and route-agreement conditions. At a
        smaller scale, the quantile proof gives a complete condition for minimizing the
        balancing objective, ties and interval endpoints included. It shows that the
        strict-count clause in Appendix C misses the upper endpoint (the interval stated just
        after it is correct). Finding that endpoint case was useful to me, because the
        theorem tells us precisely which thresholds minimize the objective, so we aren't left
        holding a counterexample alone.

Conclusion

      
The next proof I want for K3 connects the public causal state to the packed graph,
        which means showing that packing each KDA history, MLA cache, and AttnRes source
        preserves its transition. That would join the sequence theorems to the graph theorem,
        and we'd have one account of the model instead of two separate ones. Loaded weights and
        finite-precision execution would come next.

      
I'd also like to discuss the Appendix C endpoint case with people working on expert
        balancing. That count condition handles ties and interval endpoints, but the router
        still needs to choose a threshold and resolve ties. Connecting the theorem to the
        histogram implementation is what would make it useful for the update itself.

      
My hope is that we eventually release models with their equations and proofs right
        alongside the code and weights. For this one, we have concrete connections left to
        prove, and if you're interested in taking those on, I'd be very happy to work with you :)
