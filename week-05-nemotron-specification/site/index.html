Nemotron 3 Ultra: replaying a rounded state

Robert Joseph George · TorchLean Verified Examples

After Moonshot AI's Kimi K3 in the last example, I wanted to look at an open-source model from a US team too. NVIDIA's Nemotron 3 Ultra combines recurrent Mamba layers, attention, and routed experts in a model with 550 billion parameters (55 billion of them active for each token) that supports a million-token context. And NVIDIA released base, post-trained, and quantized checkpoints, along with training datasets and recipes. Nemotron 3 Ultra release ↗

I want to work through one idea: keep an older checkpoint, and when we need the current state, replay the recent inputs from it. Why bother replaying? NVIDIA explores it to cut the rounding error once the state is stored in fewer bits, and that error matters because a recurrent layer keeps overwriting its state, so rounding those numbers can affect later calculations. Let's first check when replay gives us the same state, then use FloatLib to ask what changes when we round the checkpoint.

NVIDIA's account of quantizing Ultra makes the practical choices clear. A quantized model mixes several formats (the routed experts use NVFP4, while the recurrent state cache uses FP16 with stochastic rounding), so saving memory comes down to choosing what to round, where to round it, and how to keep the rounding error small. Since we have the report and the implementation, I can follow those choices into the equations and state the assumptions my proofs need.

A language model carries information forward as it reads. Attention does this by storing keys and values for individual past tokens, while Mamba's state-space model (SSM) keeps a tensor called the state and updates its entries with each new input. Nemotron uses both. Its recurrent tensor keeps the same shape for the whole conversation, even though the numbers in it change at every step.

In Nemotron 3 Ultra, those tensors span 48 Mamba blocks. Keeping them in FP32 takes 384 MiB per main-model sequence before any other allocations, and although each request’s state has a fixed shape, that cost grows with the number of requests being served together. So the report's §4.5 saves that memory by storing the state in fewer bits, and to reduce the rounding error this adds, it also explores keeping an older checkpoint and replaying the inputs since it was saved. NVIDIA tested it in emulation on Nemotron 3 Super (the Ultra release doesn't use it yet). I start with the memory calculation, then check when replay returns the same state and how rounding a checkpoint affects later updates. In the example below you can change the storage schedule and see why a smaller error budget need not mean a smaller actual error.

Counting the state and attention cache

Ultra's released BF16 configuration lists 108 residual blocks: 48 Mamba blocks, 48 MoE blocks, and 12 attention blocks. Mamba blocks hold recurrent state and attention blocks hold keys and values. I transcribed their order as releasedSchedule (each entry names one residual block), and Lean checks the counts.

Each Mamba-2 block has 256 heads, 64 value channels per head, and 128 state coordinates. That gives a state tensor of shape [256, 64, 128], and all 48 FP32 state tensors together hold 384 MiB. On the attention side, each block has two KV heads of width 128, so the 12 blocks add 6144 bytes of FP8 keys and values for each token.

Mamba is a state-space layer: it updates a fixed-size state using coefficients chosen from the current input. A mixture-of-experts (MoE) block selects a few learned feed-forward transformations for each token. Attention instead keeps keys, which future queries compare against, and values, which their attention weights combine, so these three kinds of block have different storage needs.

Where does that 384 MiB come from? Let's count the entries. One Mamba head stores \(64\times128=8{,}192\) entries, so 256 heads give 2,097,152 entries in a block, and at four bytes per FP32 entry that's 8 MiB (here MiB means \(2^{20}\) bytes). Multiplying by 48 gives 384 MiB. The BF16 label on the model describes its weight representation, so don't read it as the precision of every working state.

The KV payload stays below the recurrent payload until 65,536 tokens, where the two meet (released_fp32_fp8_crossover checks the exact boundary). If you store the SSM state in FP16 instead, that boundary halves to 32,768 tokens. These counts cover the payload for one main-model sequence. Convolution history, scale metadata, allocator padding, MTP, and retained snapshots add to the serving system’s memory use.

Batch size matters here as much as sequence length: sixty-four active requests with separate FP32 states already require \(64\times384\,\mathrm{MiB}=24\,\mathrm{GiB}\) for this payload alone. Reducing the state to FP16 halves that arithmetic count, but it also changes what happens every time an updated value is saved, which is why the rounding policy belongs in the calculation below.

Recovering the state by replay

  
Before replaying several tokens, let's run one prepared SSM update in Lean. We retain
    [10, 0], write [2, 0], and read the first coordinate. The
    output is 12. If you hover over the tensors and step, you can see how their dimensions
    appear in the types.

  

  
  
So how do we get the current state without writing it after every token? We save it at an earlier point and keep the
    inputs needed for the updates since then, and to recover the current state we start from that
    checkpoint and run those updates again in order. Here \(s\) is the saved state and
    \(u_1,\ldots,u_k\) are the prepared inputs (the values and coefficients consumed by the
    recurrent update, after the earlier processing of each token). They aren't raw token IDs.
    Replay a token ID through a changed projection or convolution and you won't necessarily get
    back the prepared values used the first time.

  
In §4.5,
    the authors describe how they catch up from the older state:

  
we cache the input activations and apply activation replay to forward the state on-the-fly.

  
Let's make that replay step precise. We have to retain the values the update consumed,
    not resample them or regenerate them from a different state, and once those values are fixed
    I can prove the replay identity for a general transition before looking at rounding.
    (I'll use “scan” for applying that transition in order, carrying each updated state into
    the next step.)

  

    Stored checkpoint s+Pending inputs u₁ … uₖ
    →Same causal scan→
    Current state + outputs
  

  
current = scan(step, checkpoint, pending).state

    push(u): pending ← pending ++ [u]

    flush(Q): checkpoint ← Q(current); pending ← []

  
Replaying the old buffer and one new input gives the same result as recovering the current
    state and then taking one more step. That's observe_push in Lean, and
    run_from_replay extends the identity to a whole suffix, including every emitted
    output. Both reuse the causal scan from the Kimi K3 example, so I didn't write a second one.

  

    Replay.lean
    
This replay identity holds for any deterministic transition and input list, as long as the
      replay uses the same prepared inputs and arithmetic. Saving the state exactly preserves it
      (observe_flush_id_state), while a lossy write replaces it with the quantizer’s
      result (observe_flush_state), and a flush also clears the buffer’s earlier
      output history.

  

  
If a step uses randomness, replay has to keep its random choices too, and once those choices
    are fixed, the same deterministic identity applies. If you draw again on each replay, the question
    becomes one about distributions, which needs a separate theorem that I haven't written.

  
Here's a small example you can check in your head: let the transition be \(s'=s+u\), the stored checkpoint
    be 10, and the pending inputs be 2 and −3. Observing the buffer gives state 9. If we append
    input 4 and replay from 10 we get 13, exactly as if we'd started from the observed state 9
    and applied that one new update. But the identity depends on the order and contents of the
    buffer, so it doesn't let us discard the −3 or replay a newly sampled substitute for it.






  
An error budget for checkpoint writes

  
  
A rounded checkpoint can differ from the reference state in every entry. How do we keep
    track of that difference? Suppose one update bounds each coordinate error by \(L\) times the previous
    allowance (with the prepared input held fixed), and each storage write adds at most
    \(\delta\) to that allowance. Then running \(n\) updates before writing multiplies it by
    \(L^n\) and adds one \(\delta\).

  
Writing \(E_j\) for the budget after the \(j\)th checkpoint gives the recurrence:

  
Eⱼ₊₁ = L^(nⱼ₊₁) Eⱼ + δ

  
Here \(E_0\) is the error in the initial state and \(n_{j+1}\) is the number of
    tokens in the next chunk. If each update shrinks or preserves a difference between states,
    then \(0\le L\le1\), and after \(m\) writes we get:

  
Eₘ ≤ E₀ + mδ, for 0 ≤ L ≤ 1.

  
So for \(E_0\ge0\), \(\delta\ge0\), and \(0\le L\le1\), you pay at most one \(\delta\) per
    write. If updates can amplify a difference, the weighted recurrence still applies, but this
    linear bound can fail. And even under the linear bound, moving the writes changes where their
    errors enter the computation.

  
The factor \(L^n\) can make the weighted budget (a worst-case calculation, not a measurement
    of an actual rounding error) much smaller than the count-only bound. With no initial error,
    \(L=1/2\), a write allowance \(\delta=0.1\), and two chunks of two tokens, the first budget is
    0.1 and the second is \(\frac14\times0.1+0.1=0.125\), because the older allowance has shrunk
    through two updates before the new write contributes its own.

  

    Error.lean
    
quantizedChunks_within_of_writes works with arbitrary tensor shapes, sequence
      lengths, and chunk partitions, and checkpointBudget_le_count bounds its budget
      by the number of writes under the nonnegativity and retention assumptions above.

    
The WritesWithin premise asks for an error allowance at the states the
      rounded execution actually writes, because floating-grid spacing grows with magnitude and no
      single absolute cap can cover every unbounded real input. Fixed-grid quantizers can use the
      stronger uniform premise in quantizedChunks_within.

    
Both executions receive the same prepared inputs, so if a perturbed state changes the next
      sampled token, we'd need to control that change before using this comparison.

Fewer writes can leave a larger error

  
  
Table 16
    reports emulated checkpointing experiments on Nemotron 3 Super, while the released
    Ultra cache uses FP16 with stochastic rounding (described on page 46). For my example,
    I use an integer grid so you can follow every rounding decision and isolate the effect of the
    storage schedule (I'd need the report’s model and FP16 encoder to reproduce its
    measurements).

  
I'd read the table one rounding policy at a time. With FP16 round-to-nearest, its reported
    mean accuracy drop changes from 1.07% without checkpointing to 0.03% with period eight, but
    with FP16 stochastic rounding the corresponding values are −0.26% and 0.19%. So checkpointing
    helps several rows, though the table doesn't show it improving every policy.
    Our example asks the related mathematical question: does reducing the number of writes
    force a smaller terminal error for every input sequence?

  
No, and the example below shows why. It uses \(s'=as+u\) with nearest-even rounding to the integer grid, so
    every write has absolute error at most ½. If you select the cancellation example, you'll see why fewer
    writes need not decrease the actual terminal error, even when \(a=1\).

  
  
My favourite example here is the cancellation sequence −0.9, −0.9, −0.5, −0.1, with exact sum −2.4. Writing each token
    finishes at −2 (error 0.4), while writing every two tokens finishes at −3 (error 0.6).
    Half the writes, and a bigger error! Both runs satisfy their error budgets. It's the signs of the rounding errors that explain the
    difference: some cancel, and changing the schedule changes that cancellation, so fewer writes
    need not reduce the actual final error. The report’s measurements are compatible with this
    example.

      repeated_ties_lose_updates checks the other example, where two half-unit

The Mamba state update

  
  
Inside one recurrent head, the state is a matrix with one row per value channel and one
    column per state coordinate (the tensor type records this as
    [valueDim, stateDim]). For each token, the prepared input tells the head how much
    old state to retain (\(a\)), what values to write (\(x\) and \(B\)), and how to read an
    output (\(C\)).

  
S′ = aS + xBᵀ; y = S′C.

  
So the scalar \(a\) determines how much of the old state we retain, the outer product
    \(xB^{\mathsf T}\) writes new information into the state, and multiplying by \(C\) reads an
    output vector.

  
So what sensitivity factor does a Mamba update have? Start with two different states, \(S\) and \(T\), and apply the same prepared input to
    both. When we subtract, their new input writes cancel:

  
update(S,u) − update(T,u) = a(S − T).

  
Each coordinate difference is multiplied by \(a\), so \(|a|\le L\) gives the
    sensitivity condition used in the error budget. BoundedInput pairs a prepared input
    with evidence of that inequality, and the dimensions stay parameters throughout.

  
SSM.lean
    
update_sub_apply checks the cancellation,
      update_within bounds the remaining difference, and checkpoint_error
      uses those results in the checkpoint theorem. The public SSM.Sequence.run
      takes packed input tensors and returns a final state and one output row per token, and
      run_unstack identifies each row with its scan output.

  
The model source gives us a reason for the retention bound. Its rate is
    \(A=-\exp(\mathrm{logA})\) and a mathematical softplus gives a positive timestep \(\Delta\), so
    \(a=\exp(\Delta A)\) lies between zero and one. I like this part: because the parameterization gives this bound
    for every real log-rate, we can check it without looking at a single learned value.

  
Mamba2.lean
    
prepareHead shares each B/C group across its contiguous heads and scales B by Δ
      before passing it to the SSM core. prepareHead_bounded checks the retention bound
      and updateHeads_within lifts it to the tensor of all heads. As in the model
      source, the step adds the D skip and reads the updated state before casting it for cache
      storage.

  
I use the pinned model implementation
    for these equations because the report’s cache section doesn't give the complete selective
    SSM update. My adapter begins after projection and convolution, so connecting it to the full
    decoder still needs proofs that I haven't written yet for gating, grouped normalization, and output projection, among
    other operations. Its mathematical softplus also needs a refinement argument for PyTorch’s
    finite-precision threshold branch.


  
From state error to output error

  
Does a small state error give a small output error? Not necessarily, if the read coefficients are
    large. Say each state coordinate differs by at most \(e\) and both runs use the same read
    vector \(C\). Then every output channel satisfies:

  
|yᵢ − ŷᵢ| ≤ e ∑ⱼ |Cⱼ|.

  
You can't drop the absolute values. Suppose two read coefficients are 10 and −10.
    Their sum is zero, but coordinate errors of +0.01 and −0.01 produce an output difference
    of \(10\times0.01+(-10)\times(-0.01)=0.2\), because the two products have the same sign and
    their errors add. With absolute values the bound is \(0.01\times(|10|+|-10|)=0.2\), which
    covers that case.

  
SSM.read_within follows from the tensor library's matrix-vector coordinate theorem and
    mathlib’s absolute-sum inequality, and step_output_within also accounts for
    retention in the next update. Both hold at arbitrary dimensions, even with an empty state axis.
    To turn this formula into a small numerical bound, we'd need a bound on the sum of absolute
    read coefficients. I haven't established one for learned weights. A logit bound would also
    need to follow the error through gating, normalization, skip connections, and later blocks.

Rounding theory and stored bits

  
  
For nearest-even rounding, FloatLib bounds the error by half a unit in the last place
    (ULP), and Cache.roundTensor_within applies that theorem to each tensor entry, so
    if we bound all those half-ULPs by \(\delta\), we get the storage allowance needed above. Near
    zero, the theorem uses an absolute error bound that includes gradual underflow.

  
FloatLib’s real-valued grid has no upper exponent limit, so to connect it to stored bits, its
    refinement theorems require finiteness premises (an overflowing result has no real value).
    And since the released cache uses stochastic rounding, I also examine the local random
    rounding choice and the assumptions needed to preserve its mean.






  
Stochastic rounding and the mean state

  
  
Say you have a value 3.25 between grid points 3 and 4. Nearest rounding always chooses 3.
    Stochastic rounding chooses 4 one quarter of the time and 3 the rest of the time, so the mean
    is 3.25 even though each individual write changes the value. Since the state gets written
    again and again, we care about both the average and the error along an individual run.

  
FloatLib's roundQuot chooses the upper integer when the entropy residue is
    smaller than the discarded remainder. roundQuot_sum counts the choices made
    by this executable rounder, and averaging them over uniform residues recovers the original
    quotient.

  

    P(upper) = remainder / denominator

    Mean rounded value = original value

    Absolute error of each write ≤ grid spacing
  

  
Stochastic.lean
    
roundTensor_mean lifts this mean law to tensor coordinates, each with its own
      sign and grid cell. It only asks that every coordinate sees uniform residues, so one shared
      entropy word and independent words both work.
      Stochastic.roundTensor_within bounds every outcome’s error by one grid spacing,
      and with shared entropy those errors can be correlated even though each coordinate has the
      right mean.

    
The entropy residues must be uniform, which isn't automatic: reducing a uniform fixed-width
      word modulo an arbitrary denominator can bias them. Our adapter describes a local signed grid
      cell for each coordinate, with an explicit quantum and denominator, so connecting it to the
      released FP16 encoder still means checking saturation, overflow, flush-to-zero, and entropy
      generation.

    
For example, a uniform three-bit word has eight possible values. Reducing it modulo
      three gives residue zero for 0, 3, and 6, so that residue occurs with probability 3/8,
      not 1/3, which would bias a rounding choice intended to occur one third of the time.
      This denominator of three is an illustration (I'm not claiming NVIDIA's binary-format
      encoder uses one), but it shows why the general theorem needs its uniform-residue premise.

  

  
Since the prepared SSM update multiplies the old state and adds a fixed write, updating a
    nonempty ensemble of states and then averaging gives the update of their mean.
    update_mean checks this identity, and scan_mean carries it through a
    sequence when the actual ensemble’s storage perturbations have mean zero at every step.

  
That mean-zero condition must hold at the states reached during execution. Conditionally
    unbiased rounding can establish it, but checking the encoder’s mean at one isolated input
    isn't enough. And the inputs stay fixed throughout this argument. Nonlinear decoder layers
    and changes in sampled tokens need their own analysis.

  
For the example 3.25, an unbiased write can leave an error of −0.25 or +0.75, and
    averaging those errors with probabilities three quarters and one quarter gives zero.
    But neither individual write is exact. To describe one run we still need its error
    bound, and to describe the spread across runs we need a variance bound. A zero mean error
    gives us neither, and it doesn't make the stored states identical either.

Why the mean doesn't survive every nonlinear map

  
Let's carry the 3.25 example one step further and suppose a later calculation squares the
    stored value. Three quarters of the writes return three and one quarter return four, so
    the average stored value is 3.25, but the average square is

  
The mean of a square need not equal the square of the mean.

  
The difference is 3/16, the variance of this rounded value. I made this square up
    (it isn't one of Nemotron's decoder operations), but it shows that the mean-zero write error
    hasn't disappeared: a nonlinear calculation can turn its spread into a change in the
    mean output.

  
For the prepared SSM transition, fixed input coefficients make the update affine in
    the state, so we can carry the mean through it. We can't reuse that argument unchanged
    for nonlinear gates, normalization, or token selection, where we'd need to bound what
    the next operation does to the rounding error, much as squaring did in this example.




  
Losing small gradient contributions in BF16

  
  
The report's first training-divergence account
    describes a divergence after changing the output layer's local gradient
    accumulation from FP32 to BF16. Each multi-token prediction head's loss had a weight of
    0.05, the small contributions to the shared output layer were lost, and returning to the
    FP32 recipe re-stabilized training. So let's look at how a representable contribution can
    disappear during accumulation.

  
Multi-token prediction asks additional heads to predict farther-ahead targets during
    training, and their losses contribute gradients to shared parameters, including the output
    layer. Multiplying each head's loss by 0.05 reduces its gradient contribution before
    accumulation, so the accumulator has to preserve small additions beside larger values.
    Choosing a precision only from the size of each contribution isn't enough.

  
Take a running sum of 256 and add 1. The next BF16 value above 256 is 258, so 257 falls
    halfway between them, and nearest-even rounding returns 256. So in BF16, 256 + 1 = 256,
    and the 1 is just gone!
    Binary32 represents 257 exactly, and I checked both equalities in Lean with FloatLib’s
    finite-format arithmetic.

  
BF16: 256 + 1 → 256
binary32: 256 + 1 → 257

  
The contribution 1 is itself representable in BF16, so the loss happens when it's
    added to the larger running sum (these numbers illustrate that mechanism and aren't gradients
    recorded from NVIDIA’s run). There's also a second training divergence in the report, but its
    cause remained undetermined, and I don't have an explanation for it either.

  
Accumulation.lean
    
For whole gradient tensors, accumulate_within reuses FloatLib’s reduction-tree
      error theorem: we specify the addition order and bound the rounding error at each addition,
      and the theorem then bounds the difference from the exact sum of the interpreted input
      tensors.
      A uniform allowance \(\delta\) gives \(\mathrm{nodeCount}\,\delta\).

    
The theorem accepts arbitrary tensor shapes and scalar carriers. Applying it to a backend
      requires evidence of that backend’s addition order, and errors already present in the input
      gradients must be accounted for separately.

Rolling back rejected draft tokens

  
  
Suppose a draft proposes three tokens but the main model accepts only the first. Then the next
    computation has to start from the state after that first token, because a state incorporating
    the two rejected tokens would describe the wrong prefix.

  
So how do you get back to that state? Attention can discard the keys and values belonging to a rejected suffix, but a Mamba update
    overwrites the fixed-size recurrent state, so discarding token records alone can't restore
    it. Instead, NVIDIA retains a snapshot at every draft step.
    I include the initial state in the snapshot
    sequence too, so rejecting the entire draft selects that state.

  

    Initial state→Snapshot after draft 1
    →Snapshot after draft 2→
    Snapshot after draft 3

  
Speculation.lean
    
restore_eq_prefix identifies the selected snapshot with the state obtained by
      running the accepted prefix. In run_after_restore, continuing from that snapshot
      gives the same final state and committed outputs as running the accepted prefix followed by
      the continuation.

    
SSM.Sequence.snapshots exposes the states in a
      [tokens + 1, valueDim, stateDim] tensor. Row zero is the initial state, and
      snapshots_unstack identifies each bounded row with its corresponding prefix.

  

  
These rollback laws use the same causal scan and apply to any deterministic transition,
    while a random transition must retain its choices in the state or prepared inputs for exact
    replay. As for the speculative acceptance sampler, its probability law is a separate
    obligation, and I haven't proved it here.

Conclusion

    
I'd love to extend this to the token scores of the released model. That means following
      the error from the actual storage writes through replay and the rest of the decoder, then
      comparing it with the gap between the winning token and its competitors. And I think the
      cancellation example is a good reason to measure the actual error as well as carry a worst-case
      bound, since reducing that bound doesn't guarantee a smaller error on every input.

    
The replay proof takes the transition and checkpoint schedule as parameters, so if you're
      trying a different recurrent model or storage format, we can reuse that argument and
      work on the numerical assumptions specific to your update. I'd be happy to compare
      examples, so send me yours :)
